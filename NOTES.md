## Research Question 

Do personalized, task-aware microbreak recommendations generated by an on-device machine-learning model using privacy-preserving macOS interaction data reduce acute mental fatigue while maintaining or improving quality-adjusted productivity compared with fixed-schedule breaks?

## Experiment

- 90 Minute Standardised Work Session

- 4 / 6 Sessions per participant 

- 2 / 3 Sessions Control, 2 / 3 Sessions Treatment per participant

- Collect Scores, Fatigue & Effort Survey for multiple sections of the experiment

- Goal +20 participants

## Data Sources recomended by ChatGPT

- [SWELL-KW Dataset — Download](https://doi.org/10.17026/dans-x55-69zp)
  Computer activity from 25 participants, including keyboard events, editing keys, mouse clicks, and application switching, with stress and workload ratings. Start with “Behavioral-features - per minute.” Best match for developing FocusFix’s prediction model.

- [SWELL-KW — Dataset Overview](https://www.cs.ru.nl/~skoldijk/SWELL-KW/Dataset.html)
  Describes the experiment, working conditions, measurements, and questionnaires.

- [SWELL-KW — Sample Data and Features](https://www.cs.ru.nl/~skoldijk/SWELL-KW/FeatureData.html)
  Shows the minute-by-minute data structure and available features. Useful for deciding which signals FocusFix should collect.

- [Microbreak Research — Study-Level Data](https://plos.figshare.com/articles/dataset/Effectiveness_of_micro-breaks_on_vigor_fatigue_and_performance_/20753455)
  Summarized results from experiments measuring microbreaks, fatigue, and performance. Useful for economic analysis and experiment design; not individual computer-activity logs.

- [Microbreak Research — Paper and Supporting Files](https://journals.plos.org/plosone/article?id=10.1371/journal.pone.0272460)
  Review of 22 independent study samples, with supporting data. Useful for comparing break durations, tasks, and outcomes.

- [StudentLife — Dataset Downloads](https://studentlife.cs.dartmouth.edu/dataset.html)
  Smartphone activity, sleep, and self-reported stress data. Useful for exploring personal behavioral patterns, but less directly relevant to macOS interaction data.

- [StudentLife — Study Description](https://www.cs.dartmouth.edu/~xia/publication/mobilehealth17/)
  Explains the study of 48 students over 10 weeks and the relationships examined between behavior, stress, and academic outcomes.

## Important Limitations

- SWELL-KW measures stress and workload; these are not interchangeable with fatigue.

- These datasets do not directly test whether FocusFix’s personalized breaks improve outcomes.

- Check each dataset’s access conditions, license, and citation requirements before use.

## Data Collection Decisions - October 17, 2026

### What I decided for now

- For now I just want to collect the computer behavior data. I'm leaving fatigue surveys, break reminders and ML predictions out of the app.

- I haven't decided how I will collect the fatigue scores or other survey data. The survey ideas above are still plans, not features that are implemented.

- I want the app out of the way while I work. I only need Start / Stop, a timer, local saving and CSV export. I can close the window and keep it running in the menu bar.

### Events vs summaries

- I considered saving at 1 minute, 10 second, 5 second and 1 second intervals. I wanted shorter periods because I can always aggregate them later and test what predicts better.

- I don't actually need to summarise everything inside the app. Keyboard presses, releases, clicks, scrolls and app changes will be individual events with a time since the session started.

- I can use Python later to turn these events into 5 second, 30 second, 1 minute or longer features. I need to remember that more rows doesn't mean more independent people or more fatigue ratings.

- The interval I save at is not how often I need to predict fatigue or recommend a break.

### Mouse movement compromise

- Mouse movement can create a lot of events, so I won't save the whole cursor path.

- I want to process movements as they happen and save a summary every second: distance travelled, number of movement events and seconds since the last movement.

- I need to add the distance of each small movement. If I only compare the start and end, I would miss moving in a circle and returning to the same place.

- I need to keep the previous position and last movement time across intervals so pauses don't reset every second.

- I also need to save the actual duration of the last interval because it can be shorter than a second.

- I'm measuring distance in screen-coordinate points, not centimetres. I need to consider screen setup, mouse vs trackpad and pointer settings when comparing people. I can't reconstruct exact paths or mouse efficiency between clicks from these summaries.

### Keyboard / clicks / app changes

- My understanding: keyDown = a key was pressed, keyUp = it was released. Holding a key can generate repeated keyDown events, so I also want to save whether it was a repeat.

- I'm keeping Delete / Backspace events separate from other key events. I should treat them as editing, not proof that someone made a mistake. I'll add both types of down events when calculating total keystrokes.

- I want to match key presses and releases in memory to calculate hold time without saving the actual key or what was typed. I'll leave the hold time blank if the press wasn't observed.

- I'm recording left, right and other button down/up events, scroll events and generic modifier changes. When I count clicks, I'll count a down event rather than counting down + up twice.

- I only want to save that an app switch happened, not app names, window titles, URLs or document names. I'm not counting switching windows inside the same app as an app switch.

### Things to keep in mind

- I can't assume no input means a break or fatigue. Someone might just be reading or thinking.

- I need to keep stress, workload, sleepiness and fatigue separate. My SWELL target, NASA-TLX, measures workload, not fatigue directly.

- Activity counts are not productivity. I still need a task-quality score and total time including breaks for that part of the experiment.

- Later I could test typing rhythm, pauses, delete proportion, mouse movement, scrolling and changes from someone's earlier baseline. I should only use information available before the prediction.

- I need to keep participants separate when testing generalisation to new people. I can't put the same person's nearby events in both training and testing and call that a test on new people.

- I need to match feature definitions and time windows with the training data. My original SWELL model used block averages, so I'll need separate validation for live short-window predictions.

- I want to look into SENSE-42 for keyboard/mouse behavior and repeated user-state ratings. I'll need access approval first. [Dataset / access request](https://zenodo.org/records/20328099).

### Privacy and reliability

- I don't want to save typed text, key codes, cursor positions, screenshots or audio, or upload anything automatically. I still need to treat detailed event timing as sensitive behavioral data, not automatically anonymous.

- I'll keep recordings locally outside the repo and won't upload participant CSVs to GitHub. Before collecting participant data, I need to follow the approved study consent and data storage plan.

- I need to grant Accessibility permission before starting. My app doesn't change the permission itself.

- I need to account for macOS hiding keyboard activity during Secure Input (for example protected password entry) and combining mouse events. I'm collecting observed events, not a guaranteed hardware-level trace.

- I'm using elapsed monotonic time when callbacks arrive. Saving six decimals doesn't mean I have microsecond accuracy.

- I want collection to stop on sleep, screen sleep, an inactive login session or lost permission. I'll start a new session manually afterwards instead of restarting automatically.

- My files flush about every second, so I could lose the last buffered portion in a crash. I can identify an unfinished session because its metadata stays marked as recording.
